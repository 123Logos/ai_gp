考虑到你希望精简表数量、以行业标准为基准，同时保留设备验证、API Key 管理等能力，我将表优化为 **5 张核心表**。相比之前，去掉了独立的设备表，把设备信息与会话合并；用户主表保持极简，认证方式扩展列为独立表，其余功能通过验证码表与API Key表支撑。

## 精简后的数据库表设计

### 表关系概览
```
users (1) ---< (N) user_identities
users (1) ---< (N) user_sessions      (含设备信任逻辑)
users (1) ---< (N) user_api_keys
验证码表 verification_codes 独立工作
```

### 1. 用户主表 `users`
只存储系统内唯一身份及基本展示信息，敏感联系信息不放此处。

```sql
CREATE TABLE users (
    id          BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    uid         CHAR(16)     NOT NULL UNIQUE COMMENT '对外唯一用户标识',
    nickname    VARCHAR(50)  DEFAULT NULL COMMENT '昵称',
    avatar_url  VARCHAR(500) DEFAULT NULL COMMENT '头像',
    status      TINYINT      DEFAULT 1 COMMENT '1正常 2禁用 3注销',
    timezone    VARCHAR(50)  DEFAULT 'Asia/Shanghai',
    language    VARCHAR(10)  DEFAULT 'zh-CN',
    created_at  DATETIME     DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 2. 用户认证方式表 `user_identities`
每条记录代表一种登录方式，密码、手机号等均加密存储。支持第三方登录扩展。

```sql
CREATE TABLE user_identities (
    id           BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    user_id      BIGINT UNSIGNED NOT NULL,
    identity_type ENUM('phone','email','wx','apple','google') NOT NULL COMMENT '认证类型',
    identifier   VARCHAR(255) NOT NULL COMMENT '手机/邮箱/第三方openid（加密存储）',
    credential   VARCHAR(255) DEFAULT NULL COMMENT '密码哈希，仅密码登录使用',
    is_primary   TINYINT(1) DEFAULT 0 COMMENT '是否主要认证方式',
    verified_at  DATETIME DEFAULT NULL COMMENT '验证通过时间',
    extra_meta   JSON DEFAULT NULL COMMENT '第三方token等（加密存储）',
    created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_identity (identity_type, identifier),
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 3. 会话与设备信任表 `user_sessions`
将会话令牌与设备信息合并，通过 `device_id` 区分设备，`is_trusted` 标记信任状态。  
**优势**：直接判断设备是否已信任，无需额外查询设备表；支持多地登录管理和主动撤销。

```sql
CREATE TABLE user_sessions (
    id               BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    user_id          BIGINT UNSIGNED NOT NULL,
    device_id        VARCHAR(64) NOT NULL COMMENT '客户端生成的设备唯一ID',
    platform         VARCHAR(20) DEFAULT NULL COMMENT 'ios/android/web',
    device_name      VARCHAR(100) DEFAULT NULL COMMENT '设备别名',
    ip_address       VARCHAR(45) DEFAULT NULL COMMENT '登录IP',
    refresh_token    VARCHAR(255) NOT NULL COMMENT '刷新令牌（哈希存储）',
    access_token_jti VARCHAR(64) DEFAULT NULL COMMENT '当前有效access token ID',
    is_trusted       TINYINT(1) DEFAULT 0 COMMENT '是否通过第二因素验证并信任',
    expires_at       DATETIME NOT NULL COMMENT 'refresh token过期时间',
    created_at       DATETIME DEFAULT CURRENT_TIMESTAMP,
    revoked_at       DATETIME DEFAULT NULL,
    UNIQUE KEY uk_user_device (user_id, device_id),
    INDEX idx_refresh_token (refresh_token),
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**设备信任逻辑**：  
- 登录时，应用携带 `device_id`。若该 `(user_id, device_id)` 存在且 `is_trusted=1` 且未过期，可免验证码直接登录。  
- 否则要求验证码，验证成功后将该设备的会话记录更新/新建并设 `is_trusted=1`。

### 4. 用户自填 API Key 表 `user_api_keys`
存放用户自己的第三方模型API密钥，强制加密，只保留脱敏前缀用于界面展示。

```sql
CREATE TABLE user_api_keys (
    id               BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    user_id          BIGINT UNSIGNED NOT NULL,
    key_alias        VARCHAR(50) DEFAULT NULL COMMENT '识别名称，如“我的OpenAI Key”',
    provider         VARCHAR(30) NOT NULL COMMENT '服务商，如openai、system',
    encrypted_key    VARCHAR(512) NOT NULL COMMENT 'AES-256-GCM加密后的密钥',
    masked_key       VARCHAR(20) DEFAULT NULL COMMENT '脱敏显示，如sk-...x7kD',
    is_valid         TINYINT(1) DEFAULT 1 COMMENT '是否有效',
    last_checked_at  DATETIME DEFAULT NULL,
    created_at       DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user_provider (user_id, provider),
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 5. 验证码表 `verification_codes`
场景化验证码管理，支持登录、绑定设备等不同业务，内置防刷字段。

```sql
CREATE TABLE verification_codes (
    id          BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    identifier  VARCHAR(255) NOT NULL COMMENT '手机/邮箱（加密）',
    code        VARCHAR(10) NOT NULL COMMENT '验证码，可哈希存储',
    scene       VARCHAR(30) NOT NULL COMMENT 'login/bind/trust_device等',
    expires_at  DATETIME NOT NULL,
    attempts    TINYINT DEFAULT 0,
    ip_address  VARCHAR(45) DEFAULT NULL,
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_scene_ident (scene, identifier)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 为什么这样精简是合理的？

| 合并内容 | 行业参考 | 说明 |
|--------|---------|------|
| **用户主表不含联系信息** | 对标 Firebase Auth、Auth0 的 normalized profile | 联系信息属于认证渠道，应单独加密存储，避免主表泄露。 |
| **设备 + 会话合为一表** | 大量中小型 SaaS 使用 Session 表直接记录设备 | 减少一次联表，逻辑更直接；Apple/Google 的会话系统也将设备信任状态与会话绑定。 |
| **API Key 独立** | 任何平台处理第三方 Key 都会加表，如 OpenAI Platform 的 Key 管理 | 加密与权限隔离需要独立实体，合并进设置表将导致安全风险和查询困难。 |
| **验证码独立** | 标准做法，几乎所有后端模板都保留 | 高并发读写、定时清理，独立表是必然。 |

**最终套数：5张**，覆盖从注册登录、设备风控到AI Key 管理的完整需求，且严格遵循最小权限和加密存储等安全标准，完全可以支撑 AI 陪伴 App 的用户体系。
